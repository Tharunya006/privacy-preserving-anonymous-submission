{% call learn_more("Method, assumptions and limitations") %}

Model. For an ideal hash, the digest of every different input is an independent random 256-bit string. Then each flipped input bit makes every output bit flip with probability ½, independently. Four consequences are tested: balance (mean flip rate = ½, z-test), per bit (each of the 256 output bits flips half the time, χ² with 256 degrees of freedom), independence (output bits don't flip together: the Hamming distance has variance 64, χ² variance test) and relation (the two digests are uncorrelated, φ z-test).

Reading the result. "No evidence of deviation" means no test rejected at α = {{ alpha }}. It is not proof of security. With four tests per item, about 0.4 % of items will be flagged by chance, more when many reports are examined; a single flag should be re-checked, not taken as a break. Fewer than 64 flips (inputs under 8 bytes) are too few to judge.

Limitations. One base input per item and at most {{ flips }} flips; first-order statistics only — real attacks on hash functions use structured differences that these tests cannot detect. The input is ciphertext, which already looks random, so the results say nothing about the report and are expected to look the same for every report.

Preimage: find any message whose SHA-256 starts with the same t bits as the target. Candidates are "ppass-preimage-candidate:" + 8-byte counter (counter 1, 2, 3, …; one counter value = one attempt).

Second preimage: find a message different from the stored bytes with the same first t bits. Candidates are stored bytes + "|ppass-second-preimage:" + 8-byte counter — always longer than, hence different from, the original.

Budget: at most {{ job_limits.budget_factor }} × 2ᵗ attempts and {{ job_limits.time_limit|int }} s of searching; the worker process is killed after {{ job_limits.wall_timeout|int }} s. One experiment runs at a time; at most {{ job_limits.max_pending }} can be queued or running; each admin can start one every {{ job_limits.cooldown|int }} s. Results are kept in memory only.

Verification: every reported match is recomputed from scratch by the worker and again, independently, by the server. A result without a match is reported as "budget exhausted" or "time limit reached" — never as a success.

What this shows: matching t bits costs about 2ᵗ attempts, so each extra bit doubles the work. It does not break SHA-256 and is not a security score for this report: a full 256-bit match would need about 2²⁵⁶ attempts. The global synthetic toys show the same scaling over many runs.

{# ------------------------------------------------------------- mechanisms #}

Which mechanism does what for this report

  • HMAC-SHA-256 (secret key): proves each stored item is authentic and unchanged; checked before any decryption.
  • AES-GCM tag (secret key, GHASH-based, not SHA-256): checked again during decryption.
  • SHA-256 (no key): does not protect this report's content. The app uses it to store the source's token as a digest (never shown here) and inside HMAC. A plain hash cannot prove authenticity.
  • Digital signatures (public/private key pair): not used in this project.
