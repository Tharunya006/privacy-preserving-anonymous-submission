Plaintext sensitivity vs nonce randomization — two different things.

Plaintext sensitivity (avalanche, NPCR, UACI) is measured as a controlled diagnostic with a fixed nonce, a setting the app never uses, so that only the input change can affect the output. AES-GCM is AES in counter mode: one changed input bit changes exactly one ciphertext bit. That is its design, not a weakness; integrity comes from the GCM tag and the HMAC, and confidentiality from never reusing a nonce.

Nonce randomization (shown separately below each section) is what the app really does: every encryption uses a fresh random nonce, so the output changes completely — even when the input does not change at all, as the control row shows. Those values therefore say nothing about plaintext sensitivity. None of these numbers is a security score or proof of security.

The input is a generated {{ image.width }}×{{ image.height }} {{ "8-bit RGB" if image.mode == "RGB" else "8-bit grayscale" }} image (gradient background with shapes). The bytes encrypted are the raw pixel values in row-major order{% if image.mode == "RGB" %}, R, G, B interleaved (3 bytes per pixel){% endif %} — no file format, no compression. {% call learn_more("Signature vs hash vs HMAC vs encryption") %}

Signature: made with a private key, checked by anyone with the public key — shows who signed and that nothing changed, and the signer cannot later deny it. HMAC (used by this app): one shared secret key both makes and checks the tag, so only key holders can check it and it cannot prove which holder made it. SHA-256: no key at all — anyone can recompute it, so it shows only that bytes are unchanged relative to a trusted digest. Encryption (AES-GCM) hides content; it is not a signature.

Timings depend on this machine; verification is much faster than signing because the public exponent is small. The checks show the expected behaviour on one message and one key pair; they are not a proof of security.
