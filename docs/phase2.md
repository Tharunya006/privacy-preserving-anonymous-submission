# Phase 2 — Authentication & Authorization

Phase 2 of the *Privacy Preserving Anonymous Submission System*. It provides
identity and access control for the two account holders in the system —
**administrators** and **journalists (authorized receivers)** — while keeping
anonymous sources completely account-free.

Phase 2 runs standalone from `phase2_app.py`. It does not import, modify, or
depend on any Phase 1 file.

---

## 1. Architecture

```
phase2_app.py                 entry point  -> create_app()
│
└── phase2/                   the Phase 2 package
    ├── __init__.py           app factory + register_phase2() merge hook
    ├── config.py             environment-driven settings (no secrets in code)
    ├── extensions.py         db (SQLAlchemy) and csrf (CSRFProtect) singletons
    ├── models.py             User, AuditLog, Role, Status
    ├── security.py           session handling + the RBAC decorators
    ├── forms.py              WTForms: validation + CSRF tokens
    ├── services.py           business logic shared by views and CLI
    ├── cli.py                init-db, create-admin, create-journalist, ...
    ├── blueprints/
    │   ├── main.py           "/"            public
    │   ├── auth.py           "/auth"        login, logout, change password
    │   ├── admin.py          "/admin"       admin only
    │   └── journalist.py     "/journalist"  authorized journalists only
    ├── templates/phase2/     all Jinja templates (namespaced subfolder)
    └── static/phase2/        style.css, app.js (namespaced subfolder)
```

### Layering

```
HTTP request
   │
   ├─ before_request: reset_user_cache() + load_current_user()
   │      reads the signed session cookie, re-reads the User row from SQLite,
   │      re-checks status and role on EVERY request
   │
   ├─ before_request: force password change if the account holds a temp password
   │
   ├─ blueprint before_request: @role_required(...)  ← blanket gate
   │
   ├─ view decorator: @login_required / @admin_required / @journalist_required
   │
   └─ view function → service layer → SQLAlchemy → SQLite
```

Two independent gates (blueprint-level and view-level) guard each protected
route, so adding a route without a decorator still leaves it protected.

## 2. How authentication works

1. The user posts `username` + `password` to `POST /auth/login`. The form
   carries a CSRF token; Flask-WTF rejects the request if it is missing or stale.
2. The username is normalised (trimmed, lower-cased) and looked up.
   * **No such user** → a throw-away hash comparison still runs, so a failed
     login takes roughly the same time either way (no timing enumeration), and
     the response is the generic `Invalid username or password.`
3. `check_password_hash` compares the submitted password against the stored
   PBKDF2-HMAC-SHA256 hash. Wrong password → the same generic message, and
   `failed_login_attempts` is incremented. After `MAX_FAILED_LOGINS` (default 5)
   the account is locked for `LOCKOUT_MINUTES` (default 15).
4. Only when the password is correct does the **authorization gate** run:
   `User.can_login()` refuses `PENDING`, `DISABLED` and locked accounts, each
   with a message that tells the user to contact the administrator.
5. On success `login_user()` calls `session.clear()` and builds a fresh session
   holding `uid`, `role`, `created_at`, `last_seen`. Clearing first defeats
   **session fixation**: anything an attacker planted pre-login is discarded.
6. Every later request re-loads the user from the database. If the row is gone,
   the status is no longer `AUTHORIZED`, the role no longer matches the session,
   or the idle window has passed, the session is destroyed on the spot.

**Logout** (`POST /auth/logout`, CSRF-protected, POST-only so an `<img>` tag
cannot trigger it) calls `session.clear()` — no partial state survives.

### Password storage

| | |
|---|---|
| Algorithm | PBKDF2-HMAC-SHA256, 600 000 iterations (configurable) |
| Salt | 16-byte random salt per user, generated by Werkzeug |
| Stored as | `pbkdf2:sha256:600000$<salt>$<hash>` in `password_hash` |
| Reversible? | No. Nobody, including an admin, can read a password back. |
| Plaintext | Never stored, never logged, never written to the audit trail |

Because the salt is per-user, two accounts with the same password have
different hashes — precomputed rainbow tables are useless.

### Password policy (enforced server-side in `forms.py`)

Minimum 10 characters, and at least one lower-case letter, one upper-case
letter, one digit and one special character. `static/phase2/app.js` shows a live
hint, but it is only a hint — the authoritative check is the server's.

## 3. How RBAC works

Two axes decide access:

| Axis | Values | Meaning |
|---|---|---|
| **Role** | `ADMIN`, `JOURNALIST` | *What kind* of account this is |
| **Status** | `PENDING`, `AUTHORIZED`, `DISABLED` | *Whether* it may be used |

Access is granted only when **both** are right.

### Status lifecycle

```
   admin creates account
            │
            ▼
        PENDING ──── admin authorizes ────► AUTHORIZED
            ▲                                    │
            │                              admin disables
            └──── admin re-pends ◄─── DISABLED ◄─┘
```

* `PENDING` — the password works, but login is refused. Nothing is accessible.
* `AUTHORIZED` — the only state that can reach a dashboard.
* `DISABLED` — permanently refused until an admin re-authorizes.

### The decorators (`phase2/security.py`)

| Decorator | Rule | Failure |
|---|---|---|
| `@login_required` | A valid, `AUTHORIZED` session exists | 302 → `/auth/login` |
| `@role_required(*roles)` | Signed in **and** role matches | 403 unauthorized page |
| `@admin_required` | Role is `ADMIN` | 403 |
| `@journalist_required` | Role is `JOURNALIST` **and** status is `AUTHORIZED` | 403 |
| `@anonymous_only` | Not signed in | 302 → own dashboard |

The distinction matters: **401-style redirect** means "we don't know who you
are"; **403** means "we know exactly who you are, and you may not have this".

### Why the UI is not the control

Hiding a link only removes a hint. `tests/test_rbac.py` proves the point by
requesting admin URLs directly with a journalist's cookie — every one returns
403, and `test_journalist_cannot_authorize_anyone` confirms the database is
unchanged afterwards.

Roles are also **exclusive**: an admin cannot open `/journalist/dashboard`
either. Privilege does not silently cascade.

### Immediate revocation

Because `load_current_user()` re-reads the row on every request, an admin
clicking **Disable** ends that journalist's live session on their very next
click — no waiting for a session to expire.
(`test_disabling_mid_session_revokes_access_immediately`)

## 4. Database structure

SQLite, at `instance/phase2.db`. Both tables are prefixed `phase2_` so they can
never collide with a Phase 1 table.

### `phase2_users`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER | primary key |
| `username` | VARCHAR(64) | unique, indexed, stored lower-case |
| `display_name` | VARCHAR(120) | optional |
| `email` | VARCHAR(200) | optional, unique |
| `password_hash` | VARCHAR(255) | PBKDF2-SHA256, never plaintext |
| `role` | VARCHAR(20) | `ADMIN` / `JOURNALIST` (CHECK constraint) |
| `status` | VARCHAR(20) | `PENDING` / `AUTHORIZED` / `DISABLED` (CHECK constraint) |
| `must_change_password` | BOOLEAN | forces a change after a temp password |
| `failed_login_attempts` | INTEGER | brute-force counter |
| `locked_until` | DATETIME | lockout expiry, NULL when not locked |
| `last_login_at` | DATETIME | last successful sign-in |
| `created_at` | DATETIME | set on insert |
| `updated_at` | DATETIME | refreshed on update |
| `created_by_id` | INTEGER | FK → `phase2_users.id` (which admin created it) |

Database-level `CHECK` constraints mean an invalid role or status is rejected
by SQLite even if application code were bypassed.

### `phase2_audit_log`

`id`, `created_at`, `actor_id`, `actor_username`, `action`, `target`, `detail`,
`ip_address`. Append-only. Records `login.success`, `login.failed`,
`login.blocked`, `logout`, `journalist.created`, `status.authorized`,
`status.disabled`, `password.changed`, `password.reset`, `admin.bootstrapped`.
Passwords and hashes are never written to it.

### Designed for later phases

`AuditLog.actor_id` already points at `phase2_users.id`. Phase 3's
`Submission` table attaches the same way — e.g.
`receiver_id = db.Column(db.Integer, db.ForeignKey("phase2_users.id"))` — with
no change to the tables above.

## 5. How to run Phase 2

### Install

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-phase2.txt
```

### Configure

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"
# paste the output into PHASE2_SECRET_KEY in .env
```

`.env` is git-ignored and must never be committed. Without
`PHASE2_SECRET_KEY`, development mode issues a random key and warns; production
mode refuses to start at all.

### Initialise the database

```bash
flask --app phase2_app init-db
```

### Create the first admin (bootstrap)

```bash
flask --app phase2_app create-admin --username admin
# prompts for the password twice, invisibly

# or, for a generated one printed exactly once:
flask --app phase2_app create-admin --username admin --generate-password
```

There is deliberately **no public admin registration route** — the CLI is the
only way an admin comes into existence.
(`test_no_public_registration_endpoint_exists`)

### Run

```bash
python phase2_app.py            # http://127.0.0.1:5001
# or
flask --app phase2_app run --port 5001
```

Port 5001 keeps Phase 2 out of Phase 1's way on port 5000, so both can run
side by side.

### Other CLI commands

```bash
flask --app phase2_app list-users
flask --app phase2_app create-journalist --username alice [--authorize]
flask --app phase2_app set-status alice AUTHORIZED
flask --app phase2_app init-db --drop        # destructive, asks first
```

## 6. How to run the tests

```bash
pytest                    # all 148 tests
pytest -v                 # verbose
pytest tests/test_rbac.py # one module
pytest -k "csrf"          # by keyword
```

Every test runs against an in-memory SQLite database, so `instance/phase2.db`
is never touched and nothing is left behind.

| File | Covers |
|---|---|
| `tests/test_auth.py` | admin login, invalid login, user enumeration, lockout, PENDING/DISABLED blocked, logout, session fixation, open redirect, idle timeout, cookie tampering |
| `tests/test_admin.py` | journalist creation, duplicate/weak input, authorize, disable, lockout clearing, password reset, audit entries |
| `tests/test_rbac.py` | unauthenticated access, journalist→admin blocked, admin→journalist blocked, role-change revocation, forced password change, security headers |
| `tests/test_models.py` | hashing, salting, write-only password, status rules, username rules, table namespacing |
| `tests/test_csrf.py` | tokens present; POSTs without/with forged tokens refused |
| `tests/test_cli.py` | bootstrap commands, generated password strength, no hard-coded secrets |

## 8. Security measures

| # | Measure | Where |
|---|---|---|
| 1 | PBKDF2-HMAC-SHA256, 600k iterations, per-user salt | `models.set_password` |
| 2 | No plaintext passwords stored, logged or printed | throughout |
| 3 | `password` attribute is write-only (`AttributeError` on read) | `models.User` |
| 4 | Server-side RBAC on every protected route, twice | `security.py`, blueprints |
| 5 | Status re-checked from the database on every request | `load_current_user` |
| 6 | Session fixation defence (`session.clear()` at login) | `security.login_user` |
| 7 | HttpOnly + SameSite=Lax cookies; Secure flag configurable | `config.py` |
| 8 | Cryptographically signed session cookie (tampering detected) | Flask + `SECRET_KEY` |
| 9 | Idle timeout (15 min) + absolute lifetime (30 min) | `config.py`, `_session_expired` |
| 10 | CSRF tokens on every state-changing form | Flask-WTF `CSRFProtect` |
| 11 | Logout is POST-only and CSRF-protected | `auth.logout` |
| 12 | Brute-force lockout after 5 failures | `register_failed_login` |
| 13 | Generic login error — no user enumeration | `auth.GENERIC_LOGIN_ERROR` |
| 14 | Dummy hash for unknown users — no timing enumeration | `services.burn_time_for_unknown_user` |
| 15 | Server-side input validation (length, charset, strength) | `forms.py` |
| 16 | Open-redirect protection on `?next=` | `is_safe_redirect_target` |
| 17 | Jinja2 autoescaping — XSS defence on all output | templates |
| 18 | SQLAlchemy ORM / parameter binding — no SQL injection | `services.py` |
| 19 | Security headers: CSP, X-Frame-Options, nosniff, Referrer-Policy | `_register_security_headers` |
| 20 | `no-store` on authenticated pages (no browser-cache leak) | `_register_security_headers` |
| 21 | No public registration; admin bootstrapped via CLI only | `cli.py` |
| 22 | No hard-coded secrets; production refuses to start without a key | `config.py`, `_resolve_secret_key` |
| 23 | `.env`, `instance/` and `*.db` git-ignored | `.gitignore` |
| 24 | Forced change of admin-issued temporary passwords | `must_change_password` |
| 25 | Append-only audit trail of security events | `models.AuditLog` |
| 26 | DB-level CHECK constraints on role and status | `models.User.__table_args__` |
| 27 | Admin accounts cannot be disabled through the web UI | `services.set_status` |

### Known limits (honest scope for the viva)

* Lockout counters live in SQLite and are per-account, not per-IP — a
  distributed attack against many accounts is not rate-limited.
* `SESSION_COOKIE_SECURE` defaults to off for local HTTP development; it must
  be turned on when the app is served over HTTPS.
* Sessions are client-side signed cookies (Flask's default). They cannot be
  forged, but they also cannot be revoked server-side before the next request —
  in practice the per-request database check closes that window.
* The audit log stores an IP address, which is fine for admin and journalist
  accounts but must **not** be extended to anonymous submissions in Phase 3.
